## 4. 超越目标：用可验收的结果衡量

### 4.1 联合补卡，而非分别凑齐每个集合

用户可选择多个集合和目标等级，系统以精确卡片版本为采购键。一个版本若同时满足俱乐部、联赛或稀有度集合，只购买一次；分别复核每个集合的规则与贡献，不能因为同名/同球员就合并不同版本。

规划单位是“能跨过等级门槛的一组卡”，不只是逐张按积分/金币比排序。必要时保留几个单集合可行方案，再比较它们合并后的去重费用、奖励和剩余缺口；也保留更贵但有跨集合贡献的候选，不能先只保留各集合最便宜方案后再合并。

度量：同一冻结卡库、报价与规则下，对比逐集合采购的去重总费用、达成集合数、新增奖励。结果可能相同，不保证所有输入都能省钱；必须至少在有重叠收益的 fixture 中优于单集合基线。

### 4.2 两种明确目标，不捏造奖励价值

- **指定等级，尽量少花金币**：选择集合/目标，给出当前已知最低成本方案和可替代卡。
- **固定总预算，优先更多代币**：最大化同种代币的预计新增数量，同奖励时更少花费优先。不同代币、徽章、球衣不可随意折成金币相加，分别列出或按用户关注目标排序。

等级达成、奖励可领和奖励已领取是不同字段。奖励合同未核实前只显示“目录奖励/预计可达”，不得宣称已获得；若每档奖励累计发放或只给最高档，必须按实际规则决定增量，不能直接相加 D–S 文案。已领取项不再次计入收益，未知领取状态给出不确定范围。

### 4.3 可解释、可替换，价格变化后继续有用

每张待购卡说明：帮助的集合、哪个门槛/bonus 需要它、版本、参考价来源/时间、是否还有替代。没价格是未知，不是 0；第三方未收录不是已证明市场绝版。

购买前的重新规划只调整尚未执行的项目，并继续受用户批准的目标、精确候选范围和预算约束；不能用“自动优化”扩大购买范围。没有剩余批准候选时在本页说明目标差距。成交回执已确定的费用、未知扣款预留和剩余预算不能被重规划清空。

### 4.4 成本闭环，而非预计税费

分别记录预计采购、实际买入、实际卖出净收入与尚未出售的持有金额。转售是可选后续能力，必须先确认 EA 收集生效及卖出后是否保持，不预扣预期卖价来给当前采购腾预算，也不保证成交或盈利。

预约的是具体已买实体及用途；解除预约须满足收集确认与保留策略，SBC 和库存整理不能抢用未完成目标的卡。Gallery 只需版本收集时不默认套用 SBC Only Untradeable/评分限制；采购用途不反向放宽 SBC 选材。

原型仍使用明确标注的虚构进度与卡片，浏览返回、分类筛选、缺卡选择和采购清单可操作，不消费金币；生产接入仍是 G1/G4 Pending。验收新增默认打开分类总览、七分类可进入、集合/卡片与返回一致、未同步不显示假零、级别达标不等于全版本收齐、奖励未领不混算及保留原联合规划八场景。

### 6.1 集合目录如何更新（2026-09-29 源码复核）

用户明确要求集合持续随 EA 新增而更新，不能依赖逐个改代码。前述原型中的少量固定集合仅用于界面演示，不是生产目录方案；生产 UI 必须根据运行时目录渲染分类和集合，不能固定七类、126 集合或具体球队清单。

需要区分三种数据：**目录定义**（有哪些集合、筛选条件、人数/分数门槛、奖励）、**集合的卡片成员**（当前哪些精确版本属于它）、**账号收集进度**（哪些版本已收集）。刷新其中一种不等于另外两种也已更新。

| 核对项 | Fodder 本轮客户端 | Enhancer 本轮客户端 |
| --- | --- | --- |
| 集合目录来源 | `GET https://fodder.gg/api/gallery`，返回 `categories / engine / tags`；集合定义含 `slug/name/required/clubs/leagues/rareflags/holo/grades/reach` | `GET https://enhancer-api.futnext.com/galleries/categories`；界面遍历响应的 categories/sets |
| 首次读取 | Gallery 页面 `$4()` → `s4()` → `ie('/api/gallery')` | Gallery React view → `mD()` → `useQuery` → `zNe()` |
| 同页重复访问 | `s4()` 有 `e.index` 就直接返回；`indexPromise` 合并正在进行的请求，失败只清 promise 以便下次重试 | `queryKey:['galleryCategories']`，`staleTime:Infinity`，正常切换页面复用查询缓存 |
| 是否定期拉新目录 | 在已检查的调用链中未见目录 TTL、轮询或显式清除 `gallery.index`；关闭 Gallery 只清界面/选择，未清目录 | 未见目录轮询、`invalidateQueries/refetchQueries` 等针对该 key 的调用；Infinity 是不因时间自动变旧，不是永久保存，未订阅查询仍可能按库默认约 5 分钟回收 |
| “同步收集”实际做什么 | `u4()` 通过 `c4()` 使用已缓存目录生成查询范围，再调用 EA 概念球员搜索，更新 collected 历史；不重新调用目录接口 | `GAe()` 扫 EA 静态 ID 对应的概念实体；单集合先 `GET /galleries/sets/{id}/player-ids`，再扫该范围；不失效 categories 查询 |
| 卡片成员更新 | 目录提供 club/league/rarity 条件，由 EA `searchConceptItems` 返回当前版本；单集合 `g4()` 也会复用当前页面 set 缓存 | 单集合 ID 与分页成员由插件后端提供；客户端再向 EA 查询收集字段 |
| 新集合是否需要升级插件 | 已支持的规则类型下，后端目录新增记录即可供下一次读取渲染，无需逐个发布脚本 | 同样由后端数据驱动，普通新增记录无需升级扩展 |

客户端没有提供这两个后端的源码。能确认的是**更新由服务端目录提供**，不能进一步声称作者后台一定是自动从 EA 抓取、实时推送或从未人工维护。若后端未收录 EA 新集合，用户刷新插件也不会凭空发现它。新增一种客户端尚不认识的规则/奖励结构，仍可能需要引擎升级；“无需改集合清单”不等于所有未来规则无需改代码。

本轮额外做了一次无 Cookie、无认证、无账号数据的公开目录 GET，返回 `200`；响应头为 `Cache-Control: public, max-age=300, stale-if-error=3600`，未观察到 ETag/Last-Modified。载荷仍是 7 类/126 集合，与前次样本字节 SHA256 相同，不能当成已验证过一次 EA 新集合上线。`engine.version=1` 是计分引擎字段，载荷没有单独目录 revision，不能拿它检测集合是否变化。HTTP 的 5 分钟缓存与客户端的内存缓存是不同层：HTTP 缓存到期不会使 Fodder 的 `e.index` 自动失效。

公开响应与头文件保存在忽略的 `artifacts/fodder-research/gallery-catalog-latest.json` / `gallery-catalog-headers.txt`。Fodder 对应定位 `s4/c4/u4/g4/$4`；Enhancer 对应 `zNe/mD/GAe/GPt/KPt` 和 QueryClient 默认 GC。相关结论只覆盖已核验 hash 的客户端版本。

### 6.2 FCAT 自动更新合同（目录部分已实现）

当前确定的产品要求是数据驱动新增集合。以下第 1–3 条的公开目录部分已在本地源码接入；第 4 条账号进度/成员、以及第 3 条与个人计划关联的增量失效仍待实现。不能据此宣称与参考插件完全相同。

1. **目录与代码分离。** 从可替换的 Catalog Provider 获取分类/集合/条件/等级/奖励。EA 官方完整目录尚未确认可用入口。根据 §6.3 证据，已接入 FUT.GG JSON 目录优先、Fodder 公开目录降级；FUT.GG 集合卡池按单集合懒加载。两来源用独立命名空间保存，不按相同名称推定同一 ID；Fodder 没有已核实卡池接口，因此 Fodder 回退时只显示目录，不能伪造卡片或 EA 进度。两者均不依赖原插件加载，内容更新速度仍受数据源影响。Enhancer 独立请求返回 403，不能把其内部客户端标识/认证复制过来作为 FCAT 的长期方案。
2. **有界检查更新。** 首次进入 Gallery 读取目录；有缓存时先展示，距上次成功核验达到 5 分钟才发起一次目录更新；保持 Gallery 可见时按该周期检查，离开页面暂停。手动“更新集合目录”可主动刷新，重复点击合并同一个在途请求。失败至少退避 5 分钟，并遵守更长的 Retry-After；不加随机 query 绕过缓存。这个周期是 FCAT 的已批准策略，不是发现了参考插件的 5 分钟轮询。
3. **只更新变化部分。** 响应若支持 ETag/Last-Modified 则条件请求；不支持时验证 schema 后计算规范化目录内容 hash。对新增、条件/门槛/奖励变化、下线和改名分别处理；价格相关的 `reach` 变化不应让全部 EA 收集缓存失效。同 ID 改名保留关注目标与历史，规则改变只失效受影响计划，新集合标为“新”，下线不删除未决成交回执。
4. **成员与账号进度独立缓存。** 获取新目录只是一条轻量请求，不扫描全部 Club/概念球员、不触发市场查价。首次进入新增集合才按其范围读取成员/进度；已有集合发生成员/规则变化时按范围更新。名称/排序变化不重扫卡库。“同步此分类/集合”更新账号进度，目录过期时可先共用一次目录更新，不能假装旧目录上的同步就涵盖所有新集合。
5. **网络失败与未知规则可见。** 保留上次验证过的目录并显示更新时间/刷新失败；错误响应、截断、重复 ID 或未知 schema 不覆盖好缓存。缺少权威完整性证据的空目录不当作“所有集合已删除”。未知条件可显示新集合及原因，但不假装可以算分或采购；既有支持集合仍独立可用。保持季节、来源命名空间与稳定身份隔离，不仅按名称合并不同供应商数据。
6. **区分数据维护和代码维护。** 普通新增集合/改门槛/奖励通过 Provider 数据自动进入；新增规则运算符才需要引擎实现。若必须自建目录发布源，应单独管理可版本化的数据更新，不能退回 userscript 写死清单。数据源未更新时明确显示来源与核验时间；本地定时刷新无法弥补上游缺少的数据，官方目录探测和可替换来源仍是必要后续项。

自动更新验收需要补：同版本客户端新增分类/集合、同 ID 改名、阈值或成员条件变化、目录删除/空响应、旧新请求乱序、离开/返回与多次点击合并、304、缺少缓存头、超时/429 保留快照、只变参考价不重扫、跨季/跨源身份、未知规则可浏览但不能误执行。使用合成两版目录驱动回归；真实 EA 新增集合出现后再补实机证据，不以模拟变更声称全自动 EA 同步已验收。

### 10.19 Enhancer 对照与当前集合优先修正（2026-10-01）

用户要求重新核对同步速度和集合优先级。本轮确认 Enhancer 的快速展示并不来自更快的 EA Gallery 查询：它通过按 Persona 持久化的已收集版本观察（约 250ms 合并）以及不可供 FCAT 独立调用的私有聚合服务展示集合进度；其 EA 全量同步仍使用 1000 个版本分组、250 条分页和约 1000ms 页间等待。FCAT 不复制 Enhancer 私有认证、后端或用户库存上传，因此公开 FUT.GG/Fodder 卡池映射是 FCAT 额外的只读工作，必须通过缓存和进度反馈解释耗时。

本轮发现并修正两个真实行为缺口：

- Gallery 详情页“同步当前集合”此前在后台全量任务运行时被 `syncing` 禁用，且生产 `gallerySetLoader` 丢弃了 `force`，按钮可能只返回缓存。现在点击集合或该按钮都会在安全边界停止后台全量任务，优先读取当前集合，并把强制刷新传到 EA reader；完成后再恢复后台任务，保持串行，不新增并发 EA 请求。
- EA 进度原先只报告 1000-ID 组序号，组内多页时界面看似停滞。现在额外报告已完成页数和已读版本数，常驻进度条显示阶段、组/总组、页数和计数。请求批次、等待和认证/退避合同未改变。

“关注集合”继续只表示目标等级/预算偏好和筛选条件。它不是同步开关；未关注集合仍可直接打开并优先同步，未打开且没有全量证据的集合显示未同步/待核实而不是零。离线回归新增强制刷新参数、页级进度和后台抢占恢复场景，相关 Gallery 单测、同步 smoke、完整 `npm run verify`（311 文件/3497 项）均通过。真实 EA 页面仍需在登录会话中确认一次：后台进度、点击未关注集合的优先读取、单集合强制刷新发出一次 EA 请求以及后台恢复；本轮未执行 EA 写操作、买卡或提交。
