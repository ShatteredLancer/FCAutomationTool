### 2026-10-11 外部库存物化与贡献前接线（当前状态）

本节覆盖本文早期“Transfer 未接入”的历史结论。当前实现允许在 Settings 中显式把
`Unassigned` 和未挂牌的 `Transfer List` 实体纳入本批计划，但它们不能直接贡献：每个外部实体
必须先按精确 `item.id + definitionId` 写入物化 Journal，调用已核验的 EA `Item.move(..., CLUB)`，
再做 Club fresh readback，只有明确成功才进入贡献验证。Club 中同版本实体仍按原保护规则处理；活动交易、
重复信号但没有可确认的 Club 实体、属性/积分变化、未知回执均 fail-closed。

物化 Journal 为账号作用域，状态为 `pending / confirmed / rejected`。恢复只做定向 Club 只读核对：

## 3. 方案选择与库存优先

### 3.1 同一张表展示可比较的路线

保留原生 SBC 同窗口入口，增加路线列表，不跳转 Tools。默认显示最低总材料价值、少卡折中、最少卡，以及零/低待购额备选；额外价格档按当前目标的最低价值 +5/+10/+20/+30% 预算生成。总材料价值模式比较库存估值与待购之和，最低待购模式只比较待购预算，不得把网站 key 当作已知的私有算法。

每行显示：预计本次贡献积分/超额、库存张数/积分、待购张数/积分、待购总估价、采购总上限、总卡数和理论最少批次。已有材料估值单独列出，不混进待购金币。展开可看各评分/稀有度数量、候选版本、逐卡参考价/上限、受保护或缺价的原因。库存＋补卡路线用账号实际库存重新计算，不仅复制公共市场配方再机械减张数。

默认使用用户批准的“总材料价值最低”；网站 Recommended 仅作外部参考。折中路线的含义明确为在所示额外价值预算内减少卡数，不引入隐藏的 Balanced 权重。剪枝同时比较待购成本、总材料价值、未知估值数量和卡数，不能因库存待购额为零就删掉多卡低价值方案。候选/时间预算受限时标为“当前候选中最低/搜索未完成”，不宣称全球最优。

### 2026-10-08 高价库存选材修复

### 3.2 先规划完整目标，再执行库存部分

“库存优先”分为两步：生成路线时先计入适合该路线、通过用户保护的库存；执行时优先贡献其中选定的库存，随后按实际剩余积分补卡。不能先不可逆地清空库存，再发现剩余金币不足。也不能为了完全贴合网站的87配方，就排除用户已有的便宜84、85材料。

### 2026-10-09 库存被全部排除的修正

27.0.14 的一次真实规划记录显示 `materialValue:0`、路线全部为市场补卡。复核发现读取器把 `onlyUntradeable` 固定为 `true`，没有跟随 FSU 的实际 Only Untradeable 设置；当 FSU 允许可交易材料时，Club/Storage 中合规的可交易 83/84 会被全部排除。现已改为直接读取 `info.build.untradeable`，FSU 开启时仍严格过滤可交易卡，关闭时才允许符合其它保护条件的可交易库存。

Streamlined 默认仍只把 Club 和 SBC Storage 作为执行库存来源。Settings 显式 opt-in 后，Unassigned 和未挂牌 Transfer List 卡可作为外部候选，但必须经过本轮新增的精确移入 Club 事务、写后回读和 Journal 恢复保护；诊断会分别记录外部来源、物化状态、Club/Storage 分布、可交易性、接受数量和排除计数，不记录卡片或账号身份。

库存和市场数量必须共同校验达标与成本；最少卡路线可以选择更少的库存，而不是强制把所有低分卡消耗完。锁卡开关、Only Untradeable、评分范围、特殊卡/Evolution 和其它既有保护继续生效；“库存优先”不等于允许消耗全部库存，Streamlined 也不继承 Puzzle 默认82上限。所选路线需要被当前设置保护的高分卡时明确提示冲突，不自动放开。

库存不足一整批时，允许最后一批库存与第一批已购卡混合；如果先贡献库存才能释放必要的 Club 同版本位置，则先执行这个小批库存。页面始终区分已有库存、本计划已购和未购占位。

纯补卡不消耗计划开始前的库存，但仍读取冲突版本、位置与容量。同一计划恢复时的已购实体属于可用材料，不重新购买；遇到 Club 中被保护的同版本卡，优先换别的版本，不能为腾位置牺牲那张卡。

## 4. 采购支持哪些组合

当前 `src/adapters/ea/fc27-puzzle-buy.js` 使用精确 `defId:[definitionId]` 搜一个版本，搜索能返回多条拍卖；每次 `service.bid` 只买一条，回执绑定精确实体。现有底层可以串行买 A、B、C 等不同球员，不存在“一批只能同一球员”的要求，也没有一次请求买30张的现成接口。

| 组合 | 方案处理 | 证据/限制 |
| --- | --- | --- |
| 不同球员、相同评分/稀有度与积分 | 同配方桶内轮换，凑同一贡献批次 | 每个版本独立验证资格/价格；不是把 OVR 相同视作一定等价 |
| 不同评分/积分的球员混合 | 允许，如87与86混合 | 必须更新实际积分、剩余数量和预算 |
| 同版本，跨多个贡献批次重复买 | 支持的基线策略 | 前一实体确认消耗、Club 冲突解除后再买下一张 |
| 同版本，在同一批同时买多份 | 有条件能力，不作为首版默认前提 | 必须证明暂存、移动与提交路径可处理多个精确实体；不能假设可交易卡进入 SBC Storage |
| 一次搜索多个不同 definition ID | 后续优化候选 | 当前 FC27 OR 查询/评分过滤合同未验证，不能据数组字段假定支持 |

因此最低价配方的“1355张84”是需求总量，不是同一个球员可以买1355张，也不是市场库存已证明足够1355张。建议每批优先用不同合格版本，下一批继续复用刚消耗版本。

一次查询中的其它拍卖可短期保留为候选，避免重复获取同一批数据；但每条仍要分别买断，检查到期/已使用 trade ID/价格上限。该优化在 Streamlined 独立调度层实施，不悄悄改动已验收的 Gallery/Puzzle FSU 买卡行为。不能靠并发30个买断加速。

## 5. 动态组批，而不是固定买满30张

全局保留评分/积分桶的剩余数量，执行时只物化下一批精确卡片与拍卖。每批上限读当前 EA 已验证能力；现有原生选择上限观测为30，不宣称所有 SBC 服务端永远固定30。

流程：

1. 核对当前目标、已确认积分、库存和本次授权；选择尚未消耗的允许库存。
2. 若仍需购买，按配方缺口、同版本冲突和单卡上限选下一批候选，串行搜索/购买/核对入库。
3. 买不到一个球员时，先尝试同配方桶的其它合格版本；达到每卡已配置尝试次数后记录失败，不自动涨价。
4. 根据以下收批条件关闭当前批次，精确复核已拥有材料，再执行已获用户授权的贡献。
5. 确认 EA 进度、实体消耗和容量变化后继续；只更新剩余配方和必要尾部，不每批重新扫描全卡库/全市场。
6. 达到当前一次目标即停止；奖励、刷新后重复下一轮属于另一个已记录的实施阶段。

收批条件：达到当前上限；已有待贡献分数足够结束目标；可用暂存/版本位置已用尽；经过有界的候选轮换仍无平价新卡；用户点“贡献已就绪卡”。不足30张可提交，0张不能发贡献请求。

建议初始的“平价搜卡等待”规则为：已至少完成一轮可用候选轮换，且连续60秒无新增成交则收批；用户可配置该无进展时限，不将它伪装为原插件默认行为。单卡尝试次数沿用现有 Settings，不新增一个隐含的无限重试循环。0张且一轮候选耗尽则暂停并提供刷新报价/重试/改选路线；有卡且提交后缺口仍在时继续下一批，但不能立即无间隔重查全部刚失败版本。

例：30张目标只买成18张，其余在上限内无货，达到收批条件后贡献这18张，读取实际新增积分，再补下一批。不是整批判失败，也不是自动抬价凑30。若这18张足够达标，就不再买后面的12张。

上述少量继续只适用于明确无货/明确抢单失败；未知扣款、未知入库或未知贡献不能当作普通无货。用户 Stop、登录失效、限流或账号/目标变化后，不暗中追加贡献；保存已确定进度，按请求种类核对未知结果，再由恢复流程继续。

## 6. 价格、替换、授权和恢复

- 沿用 Settings 的 FUT.GG/FUTBIN/Both 许可与购买参考；实际规划/购买只使用选定购买基准，复用有效缓存。EA 只提供可成交挂牌，不作为估价回退；缺价不当零价、不偷偷换源。
- 每张实际成交不超过合法价档处理后的已批准上限；价格向下对齐时可能买不到，不得为了凑整向上突破授权。批次按实际成交计费，估价与上限分开展示。
- 总预算检查同时包含已确认花费、发出但未决的最大扣款、其余必要采购预算。有限路线不能因为之前买得便宜，就擅自提高后续某卡上限。
- 一次批准冻结“当前一次 SBC＋库存实体＋配方桶与可替换候选范围＋逐卡上限＋总预算＋到期时间”。同桶换球员仅在此范围内自动轮换；换评分路线、扩大可用库存、加入未授权版本或增加上限需显示剩余新方案并由用户批准。
- 选择路线只生成预览，不直接消费。用户已要求按本计划分步实施，现接入明确写出永久消耗的“按方案购买并贡献”有限任务入口，一次同时批准当前目标的采购与贡献，范围内不逐批弹窗。开发授权不等于 Agent 获得实际交易或贡献授权；真实操作仍由用户点击。
- 每笔买入、移动、贡献分别保存 run/wave/采购槽位/auction/item/版本身份与回执。购买成功不等于已经入 Club，更不等于已经获得积分。
- 刷新恢复只核对本计划尚未结清事务；已贡献的实体和已买材料不重买。旧目标的确定历史不阻断新 SBC；未知交易仍保留并沿既有生命周期核对，不用清记录掩盖问题。
- 恢复时新报价可更新展示，不能改写旧授权；报价或授权过期时先核对已发生的交易，再明确提示继续所需动作。已贡献材料不可回滚；未贡献买卡留在已确认位置，不自动出售。

## 7. 数量大时的算法与请求成本

当前 per-copy 展开上限为1000/版本，总候选20000，且依赖 `availableCopies`。不能仅提高上限来处理1355张需求，也不能把需求量填进 availableCopies 冒充供应量。

采用两层模型：

- 配方层：按资格、积分、评分/稀有度、价格档和路由差异聚合，用整数数量求 cover；库存数量有界，市场需求数量与已观察供应分开。先获得可行低成本路线，再生成不同预算下卡量较少的非支配路线。尾部使用小规模精确/有界搜索补齐，避免单纯金币/分贪心造成昂贵补尾。
- 执行层：仅展开当前批次（及有限下一批候选）的具体版本、拍卖和实体。使用实际成交和剩余目标校正，无货版本短期降优先级，已查询 trade ID 去重；不能把旧一次搜索永久当作实时库存。

网络读取按阶段去重：挑战需求按指纹缓存；库存用已有可靠快照并在贡献前按合同精确验证；同一版本报价合并/复用有效缓存；当前市场挂牌需有界刷新，不能承诺永不再请求。目录缓存以赛季/平台/规则版本区分，绝不把 Gallery 分数缓存当作 SBC 分值。

性能验收：1000+需求不展开指数级组合，规划在工作线程或可让出主线程的分段任务运行；显示阶段、候选桶、搜索节点、当前最佳金币/卡数和耗时，可取消。执行显示已贡献/目标、已购/剩余预计、已花费/预算、当前批就绪X/上限、搜索/成交/失败状态。批次数因少量收批会增加，应标为“理论至少N批，已完成M批”，而不是固定百分比永远卡住。

## 8. 必须纳入的边界

1. 首批库存贡献前确认整个目标的剩余估价与预算可行；市场未来供应仍不能保证，明确部分贡献不可撤销。
2. 尾批按已确认积分＋已买未贡献材料计算，避免超买；超额不假定结转到下一轮。
3. Club 同版本被保护、已有未分配重复、Storage/Transfer 满、不同 pile 的同版本副本分别处理；不把信号当实体，也不顺手清理用户其它卡。
4. Gallery 的新购去向设置不能未经验证直接继承到 SBC；首版用已验证的可贡献路径。若要求 Unassigned 暂存/同版本批量，先补原生路由证据，不悄悄覆盖账号设置。
5. FUT Champions、不可交易市场版本、进化、租借和不可买版本排除采购；同款外观或同积分不证明可交易/可获得。
6. 多版本同球员、多个同版本实体按不同身份处理，不能借用传统 Puzzle definition 唯一约束阻止合法重复，也不能复用同一 item ID。
7. 当前资格存在 AND/OR、最低评分、特定稀有度/联赛时，路线和替代球员均重验；无法验证市场版本积分时只展示外部参考，不购买后才发现不合格。
8. 平台、赛季、账号、Challenge、完成周期和到期改变，使旧未执行部分失效；后台标签页休眠或限流不能靠狂发请求追赶。
9. 用户手动买卖/消耗材料或其它插件修改进度，重新对账保留确定成交；共享锁防止 FCAT 自己并发买卖/贡献，同账号跨标签也需处理。
10. 页面完成/关闭不能丢失已接受回执；奖励类型（包括 Pick/未分配）和刷新规则单独处理，不把达分等同所有奖励已领取。
