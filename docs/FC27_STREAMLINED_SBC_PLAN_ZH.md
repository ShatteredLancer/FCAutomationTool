## 1. 结论

Streamlined SBC 应作为 FC27 的独立业务类型实现，不能把传统 Puzzle 的 11 人阵容、阵容评分、化学和保存阵容流程换一个名称继续使用。它的核心是“某个 Challenge 的累计积分进度 + 一次或多次材料贡献”。`Upgrade / 83+ Upgrade / 2500` 可以作为首个验收样本，但 `2500` 只代表当前页面读到的目标，不能写入全局规则或硬编码每张卡的分值。

建议采用“原生页面增强 + FCAT 后台规划器 + 原生提交事务”的路线：

1. 从 EA 当前运行时读取 Set/Challenge 的类型、已提交积分、目标积分、资格条件、批次上限、重复与奖励状态。
2. FCAT 在原生 Streamlined 页面内增加紧凑的进度、库存预览、成本/保护策略、一次规划和继续执行入口。
3. 首个可用版完成单个 Upgrade 的“规划 → 必要时分批贡献 → 达标/部分进度 → 恢复”，不是只做预览或只能提交一批。完成后再开启下一轮的重复循环后置。
4. 成本必须区分新增待购花费和消耗材料价值；当前买卡规划按待购总成本优先记录，同时遵守 FSU 的 Only Untradeable、锁卡、Evolution、Active Squad、特殊卡和交易状态保护。Fodder 的 Lowest coins 实际展示材料总估值，不能冒称两者相同，差异见 §3.4。第三方价格不能用于推断积分。
5. 买卡不是先买再凑分：从规划阶段联合考虑已有实体、市场版本、数量和分批路由，形成同一份采购与贡献计划。默认范围为“库存＋补卡”，另提供“仅购买材料”；只读库存范围仍保留，详见 §3.5。

当前工作区已有积分 SBC 的历史设计和安全基础，但没有可宣称生产可用的 Streamlined 写入实现。已有文档中的 P3/P4 是计划，不是本次已完成的功能。

### EA 与当前代码

- EA 官方 FC27 FUT Deep Dive 说明了 Streamlined SBC 的方向：物品按 OVR/稀有度贡献积分、允许分批提交、可累计进度、可以使用重复版本；传统 Challenge SBC 仍然存在。
- 已登录实机确认 83+ Upgrade：Set 31 / Challenge 61，`isOneClickChallenge() === true`，`scoreRequirement:2500`，`submittedScore:0`；界面最低 OVR 45，Club/SBC Storage 两个页签。当前 Set 为 `repeats:1 / repeatabilityMode:REFRESH`，不能据此开放无限循环。
- 当前原生 ViewModel `getSelectionLimit()` 返回 30，实现读取 `_pageSize`；Configuration 的 `ONE_CLICK_SBC_SUBMIT_LIMIT` 却返回 0。30 是本次已验证的选择上限，不能硬编码成全部 SBC 的服务端批次上限。Fodder 使用 30 兜底也不是 EA 服务端契约。
- 单卡预览使用原生实体 `sbsScore`，当前页 49–64 普通铜卡为 20、65–66 银卡为 35；这是样本，不是完整积分表。不能把 Gallery 集合加成/FO 倍数直接用于 SBC。提交响应、超额、奖励与跨批次仍待独立采集。
- `docs/FC27_MIGRATION_PLAN_ZH.md` 已明确未确认项：精确积分表、超额处理、批次上限、重复/重置、可提交 pile、部分提交、奖励领取和 Holo/Evo 身份都不能猜测。
- 当前 FCAT 的传统 SBC 与 Gallery 计分缓存可以复用身份、账号隔离、报价缓存、日志、Journal 和恢复框架；传统 `SquadPlan`、阵容保存和化学求解不能复用为 Streamlined 的业务模型。

### Fodder GG

本次检查了公开页面、loader、远程客户端 1.3.3，并在专用浏览器核对实际加载包 hash 一致、完成五种预览。EA 会话沿用；未登录 Fodder、未订阅 Gold、未提交材料。行为包括：

- 页面内在 EA 的 One Click SBC 工作区插入入口；不是另开一个脱离 SBC 的工具流程。
- 读取 `scoreRequirement`、`submittedScore` 和 EA 的 One Click 每批上限，计算剩余积分。
- 调用 Fodder 自己的 `/api/solve-streamlined` 规划服务；请求中包含 eligible pool、过滤器、平台、每批上限、目标、`allowPartial`、`allowCopies`；`pointsPrefer` 为 `coins / balanced / cards`，不能与传统 SBC 的设置混淆。
- 返回多轮/多批方案，每批显示积分；支持最后一轮 partial，提交前在预览中选择批次。同一次执行按已规划批次串行贡献，不是每批必重新求解；下一次 Solve 才重新以当前进度计算剩余量。
- 处理概念卡、市场候选、买卡入口、Storage/Unassigned 过滤和 409/soft-ban/取消等结果。

- `https://fut.to/` 当前可访问，官网显示 FC27、`27.0.0` 和 Tampermonkey 自动更新。公开安装脚本是薄 loader，通过 `https://api.fut.to/futweb_tools/version.json` 获取版本，再加载远程代码；完整实现不在公开 loader 中。
- 官网功能页目前只承诺价格/Meta/本地缓存等通用功能。FC27 延迟公告反而明确指出新的 SBC 积分规则对旧逻辑冲击很大，并提醒官网描述可能与实际功能有差异。
- 因而 Futto 是需要观察的闭源参考实现，不是可直接复用的代码或可信 API。不得把 Futto 与本地 FSU 26.09.9 同时在同一账号上启用写入 Hook，也不能把其远程代码、账号信息或请求凭证带入仓库。

## 3. 目标产品行为

### 3.1 入口与页面

以下为待确认的交互建议。经实测建议以 Fodder 完整流程作为主交互基线：原生工作区入口 → 当前 SBC/全局设置 → 同窗口规划进度 → 批次结果 → 独立贡献。Futto 用于参考原生卡片价格/保护提示，不额外建立第二套选材入口：

- 原生 Challenge 标记为 `Streamlined` 时，在工作区对应位置增加 `FCAT 积分解题` 入口，窗口和按钮布局按 Fodder 参考，不跳 Tools。
- 页面顶部显示 `已提交 / 目标`、剩余积分、当前 Challenge、截止时间和“本次计划”状态。
- 中部显示选材摘要：已有卡、待购卡、预计积分、超额积分、预计花费、保护/跳过数量和计划完整性。
- 设置保留上次选择，不要求重新填写或再次选择 Challenge；规划、批次预览与缺卡购买沿用同一窗口。结果表含缩略卡、评分、来源、积分、材料估值；另明确显示待购总花费，不把已有卡标价当作扣款。
- 完整方案显示批次勾选和贡献；不足方案明确显示“已提交＋本次＋还差”，用户可独立确认部分贡献。未知回执先原位对账，不重复发出提交；纯预测不足不能自动消费卡片。
- 本次不默认引入“跳过设置直接提交”或另一套原生 Review Selection 串接；若希望一次点击按已存设置直接生成预览，作为简化交互的明确差异另确认。原生手动操作仍可用。
- 传统 SBC 页面继续使用原来的解题入口；未知类型显示 unsupported 并保留原生操作。

### 3.2 规划目标

硬约束先于成本优化：当前账号/Challenge、精确实体身份、资格、FSU 保护、pile、容量和交易状态必须已知。通过硬约束后按以下顺序排序：

1. 待购卡总成本最小；
2. 已有材料价值最小，避免库存方案购入成本都为 0 时任意消耗高价值卡；不可交易卡仍有材料机会成本，未知价不按 0 处理；
3. 同成本时降低无收益的超额积分、提交次数，并优先用户允许的重复材料；超额是否结转须先核实；
4. 保留后续 Challenge 明确需要的材料和保护卡。

Planner 采用有界 knapsack/cover 搜索，不穷举全部实体组合：先按积分、资格、OVR、稀有度、库存来源和公共报价聚合候选桶，再以精确 item ID 展开小候选集。达到节点/时间预算时返回 `partial` 和最佳已知方案，不能把预算耗尽伪报为“无解”。LLM 只可作为解释或候选排序的可选助手，不能决定实体资格、金额或提交授权。

以上成本优先级属于规划建议，实施前固定验收例子，不把它标为 Fodder Lowest coins 的等价实现。三态目标若全部提供，Fewest cards 允许以更多估值/超额换更少卡，但只有用户显式选择时生效；Balanced 的后端权重未知，未经确认不自创权重并声称一致。每积分价只可用于候选排序/搜索起点，不能宣称贪心结果全局最优。直接读取当前资格和材料设置，不自动继承 Puzzle 默认 82 上限，也不因目标为 2500 放宽已批准材料保护。严格区分“达标但搜索未穷尽”和“积分不足的部分贡献计划”。

### 3.3 提交与恢复

- 每次提交前保存不可变计划指纹：账号、赛季、Set/Challenge、进度、精确 item IDs、预计积分、批次和资格版本。
- 提交前再次定向验证 Club/Storage/Unassigned 实体；概念卡只能表示待购候选，不能充当已拥有材料。
- 只把 EA 明确接受的 pile 送入原生 Streamlined service；未知 pile、未知响应或账号/Challenge 变化立即停止。
- 成功、部分成功、拒绝、429/soft-ban、未知回执分别记录；未知回执不得重试同一材料。
- 提交后重新读取进度和库存，以服务器进度为准使旧计划失效。刷新/F5/重新打开页面应从 Journal 继续，而不是重复贡献。
- 奖励先做到正确识别和待处理记录；只有确认 Web App 奖励领取合同后才自动化领取。不能因为看到进度增加就声称奖励已到账。

### 3.4 参考一致性与需要确认的差异

| 项目 | 参考实现 | FCAT 计划与状态 |
| --- | --- | --- |
| UI/操作步骤 | Fodder 原生入口、两类设置、批次结果、购买/贡献分开 | 建议作为主基线，按实际界面实施；不自创多层菜单 |
| 求解位置 | Fodder 私有服务端，带库存池与规则 | 建议本地有界整数积分 cover；属需确认差异，公开客户端不能提供其私有求解算法 |
| 默认优化目标 | Fodder 最低材料估值 | 2026-10-08 用户批准最低总材料价值（库存＋待购），待购优先作为选项保留；不称与 Fodder 私有算法等价，不允许借此放宽受保护材料 |
| Balanced/Fewest | 三种偏好已实测，Balanced 权重不可见 | Fewest 可定义明确目标；Balanced 保留待确认/后置，不编造相同算法 |
| 价格/报价快照 | 私有服务、缓存可能不同步；Futto EA 回退 | 沿用已批准 FUT.GG/FUTBIN/Both、统一冻结快照和限价，无需重新请求价格合同授权 |
| 材料保护 | Fodder 本次允许可交易、评分至 96 | 沿用既有 FSU/FCAT 保护与用户设置，不能复制宽松默认而扩大材料授权 |
| 提交重试/进度 | Fodder 通用 timeout 重试、预计进度回退 | 保留既有 FCAT 未知回执对账与服务器确认原则，明确属于差异 |
| 贵重卡保护 | Futto 同 OVR 比价≥2拦截、在阵卡保护 | 不自动添加新的二倍价硬门槛；是否加可选提示/开关需确认，不与现有 FSU 策略混淆 |
| 同目标分批 | Fodder 先规划全部批次，串行提交 | 首版纳入，批前复核，实际进度偏离即重算/恢复，不自动开始下一次奖励循环 |

用户已授权按计划实施完整功能，将人工验证后置；这不是限制最终产品只能预览。当前已取得的原生证据足以实现预览和离线事务，但贡献/购买的生产接线仍须补齐请求、响应及回执合同，不能猜测未知 EA 行为。

### 3.5 库存与市场联合规划、批量购买

2026-10-06 用户要求将买卡方案并入当前计划。本节记录完整目标流程与实施依赖；不表示已实现、已确认未知 EA 路由或授权 Agent 实际买卡/贡献。沿用 §3.1 的同窗口操作，复用现有购买结果与失败重试窗口，不另加采购菜单。

#### 范围与成本

- **库存＋补卡（默认）**：联合比较只用允许消耗的库存、库存与少量购买混合、购买便宜材料并保留已有卡等组合。不能先固定一组库存，再把缺口机械交给市场求解。
- **仅购买材料**：新计划不使用原有库存作为贡献材料，但仍读取持有关系与容量来安排购入副本。恢复同一计划时已经成交的实体属于本计划已购材料，不再购买第二遍。
- 原有“仅库存”的无采购路径继续可用；界面尚未接通真实购买时不能展示可执行的补卡按钮。
- 默认按**库存估值＋本计划剩余待购总价**最小排序；同总价值下再比较待购成本、材料估值、超额、卡数和 Storage 偏好。未知库存价值不能当零价。最低待购额为独立选项；库存估值不计入实际采购花费或购买上限，必须分别显示。
- 已确认成交金额单列为已花费；恢复时展示“已花费＋剩余待购估价/上限”，不把已经扣除的金币再次计入待购预算。保留全体材料估值作为第二参考，计划比较使用同一价格快照。

#### 生成采购计划

1. **确认剩余积分**：从当前 EA Challenge 读取目标、已提交值、资格、重复状态和可用批次能力。剩余值为 `max(0, target - submitted)`，例如 2500 已贡献 400，本次仅规划 2100；到执行前再复核，不能沿用过期缺口。
2. **筛选市场候选**：复用已接入的公开球员目录与缓存，按当前资格和材料政策筛版本；库存用精确 item ID，市场用精确版本及计划数量。候选身份、资格或 SBC 积分无法验证时不进入可执行采购池，不能用 Gallery 集合加成/FO 倍数、价格或 OVR 直接猜分。
3. **读取报价**：遵守账号 FUT.GG/FUTBIN/Both 读取许可及选定购买参考，优先有效缓存、合并重复版本的请求，只读有限候选所需信息。Both 不代表两源平均或缺价自动换源；购买与 Puzzle 一样只按所选购买基准制定上限。记录来源、时间和报价版本，不调用 Fodder 私有求解器，不采用 EA 参考价回退。EA 市场仅在实际购卡阶段查找已批准上限内的挂牌。
4. **缩小搜索范围**：按积分、资格、来源和成本建立候选桶，以单位积分成本提供排序起点；保留能填补小缺口的低分卡，以及库存重复、容量/路由受限的非等价候选。分批扩展候选，不能因为首批没有结果就声称全市场无解。缺价/过期/目录不完整单独显示。
5. **本地联合求解**：有界整数积分 cover 同时计算已有实体与待购版本数量。每个已有 item 最多使用一次；同版本多次购买须对应不同未来实体，数量受预算、目标和可行路由约束。比较采购总价，不只比较平均单价或全体材料估值。单位积分价贪心只能作起点，不能代替组合比较。节点、阶段、候选数和耗时可见；预算耗尽返回最佳已知方案及搜索未完成标记。
6. **同时安排批次**：输出每批所需已有/待购材料、预计积分、购买/入库/贡献顺序、容量要求与前一批完成依赖。不能先生成便宜但无法暂存的采购清单，再在执行时临时想办法。

示例仅用于验收：本轮已验证样本 84 卡 830 分、铜卡 20 分，`3×830＋20＝2510` 是一个候选组合；规划必须继续比较 85＋83、其它合法版本或库存混合。市场价格和积分应在运行时读取，不硬编码三张84配方、当前价格或统一评分积分表。

#### 预览、购买、重试与贡献

预览必须显示：当前/目标/剩余积分、已有材料、待购版本及数量、来源、各卡积分与报价、待购总估价、逐卡上限及本次购买授权总额、材料估值、预计超额、批次数与路由限制。报价是估计，不能承诺上限内一定买到；缺少关键身份/积分/路由的方案只能说明缺口，不能自动进入购买。

用户点击批量购买后，复用现有 Gallery/Puzzle 的公共报价策略、账号单卡限制、固定/百分比溢价、默认每卡 3 次尝试（含首次）及可配置次数；不另建一套涨价算法。成交通过精确回执绑定到本 Challenge/计划/采购槽位，替换市场占位后核对资格与积分。库存 Only Untradeable 不全局关闭；用户本次明确购买的可交易材料仅按精确成交实体授权使用，不扩展到原有可交易库存或同版本其它副本。

| 结果 | 原购买窗口的处理 | 后续边界 |
| --- | --- | --- |
| 明确买到并完成既定入库/暂存 | 更新已购列表、实际金额与对应采购槽位 | 同一实体不重复购买；可进入贡献前复核 |
| 上限内无挂牌、明确抢单失败、达到尝试次数 | 保留其余成功结果，列入失败卡 | “重试失败卡”默认沿用原上限；用户可编辑本次重试上限并主动批准，不改账号默认设置 |
| 想换版本或剩余组合 | 提供“重新规划剩余缺口” | 纳入已购且未贡献实体，核对当前已提交积分；旧未执行采购计划失效。新增替代采购须按新明细批准，尤其不得静默增加总额或单卡上限 |
| 成交/扣款/移动结果未知，或账号/Challenge 变化 | 停止并在原位显示核对与恢复信息 | 先按 Journal 对账；不能归类成普通失败而重买 |
| 仅部分批次材料齐全 | 显示可贡献批次及贡献后仍差多少分 | 购买授权不是贡献授权；只在用户明确批准的贡献范围内执行，不自动消费其它卡 |

贡献前由用户明确启动所选批次，之后后台逐批核对实体、资格与实际进度；不要求每张卡再确认。需要后续购买时，必须已具备该采购波次的有限购买授权，不能因前一批已提交就扩大采购范围。真实进度偏离、卡片被手动使用、价格失效或期限变化时，保留已购/已贡献记录，从剩余部分恢复；不承诺回滚已经贡献的材料。

#### 同版本重复购入与容量

积分规则允许重复版本，不等于 Club 可以同时持有多个副本，也不等于可交易购入卡可以进入 SBC Storage。S0/S5 必须分别确认 Unassigned/Club/Storage/Transfer 的可用路由、容量和贡献前必要的移动；未确认的路由不能用假设填补。

若无法同时暂存多张同版本，计划可采用“买入一批 → 核对 → 已授权贡献 → 确认释放容量 → 再买下一批”。每个采购波次依赖上一批的确定回执；同一 item ID 不可跨批重复。若允许的路径仍不可行，则换不同合法版本，或明确显示容量/重复冲突，不能静默购买后滞留。

Streamlined 的同版本多实体合同独立于传统 Puzzle 的 definition 唯一约束，不为支持此功能修改传统 SBC 保护。购买 Journal 与贡献 Journal 按同一计划关联，分别记录成交、当前位置、贡献结果及剩余数量；重登/刷新恢复前先对账两者，不能只看“购买成功”就认为积分已计入。

## 4. 与 FSU 26.09.9、Futto 的兼容边界

### FSU 26.09.9

FSU 继续拥有 Club 缓存、材料策略、锁卡和传统一键填阵的权威实现。Streamlined 首版通过 Adapter 读取其只读策略和实体快照，不修改 FSU 源文件，不伪造 `ready`，也不复制第二套 Club 服务。FSU 的 provisional 数据在贡献前必须按精确 item ID/definition ID 定向向 EA 验证，遵守 `FSU_CLUB_CACHE_INTEGRATION.md`。

Streamlined 不调用 FSU 的传统“填阵/保存阵容”按钮；它只复用已验证的保护判断和身份校验。两者在同一页面同时加载时，FCAT 只接管带有自身 data attribute 的入口，采用命名空间、事件委托和 capability 检测，避免替换 FSU Controller/Service 原型。

### Futto

Futto 仅在本次隔离观察临时启用，结束恢复禁用。可核对公开 loader/发布包，不将其代码导入 FCAT，不假定有复制授权，不共享 EA 凭证。切换插件必须刷新或卸载页面，Tampermonkey 开关不会移除已经执行的 Hook；Futto 的销毁逻辑还会恢复原型方法，可能覆盖后来插件的 Hook，不用运行时热卸载来宣称兼容。后续以最新 FCAT 构建分别测试同一输入。FCAT 锁不能约束不参与该锁的插件，不能声称同时加载即可保证互斥。
