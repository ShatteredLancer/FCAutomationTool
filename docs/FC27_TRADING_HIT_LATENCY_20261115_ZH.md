# Trading 搜索命中到买入延迟调查与改进方案

## 结论与范围

用户要求参考 Enhancer Trader，调查 87 任务搜索命中后约 8.9 秒才返回购买错误的原因。调查阶段先完成静态调用链对照与生产 native port 的离线计时；随后用户批准实施。当前H1–H3代码和自动回归已完成，最终构建已专用安装，H4真实页面/成交验证仍待账号进入。详细阶段记录见末尾，不能据此宣称历史403已定位或真实抢购已验收。

历史 8,890ms 是搜索响应到购买失败结果，包含准备、等待和响应，旧日志没有 bid 实际边界时间。当前 FCAT 在 buy preflight 强制重读 Unassigned、Transfer，随后 send 再过通用 pace；三次请求均以 3,000ms 起始间隔串行。搜索前已做过同样两项读取，命中后重复了它们。

离线 `node artifacts/market-hit-latency-probe.mjs` 使用生产 `createFc27MarketTaskNative`、现有合成 EA 服务及假时钟：搜索响应 t=6,000ms，买入边界 t=15,000ms，中间调用严格为 Unassigned → Transfer → bid，零网络响应耗时仍增加 9,000ms。它隔离出代码人为等待，并非将现场 8.890 秒逐毫秒归因；实际网络耗时会占用请求起始间隔，调度/存储另有开销。此控制未发真实 EA 请求。

## Enhancer Trader 实际行为

参考本机研究副本 `artifacts/fodder-research/enhancer-27.0.0.4-readable.js`，SHA256 `8b92b890401292f9a0c569109ff95d203843def5fd430a9ee480d37dd9539b0b`。这是可核对的 Trader 实现，不宣称线上最新；不能用另一份新版 PurchaseItems 批量购买替代 Trader 证据。

| 步骤 | 原版证据与行为 | FCAT 当前差异 |
|---|---|---|
| 搜索周期 | 745、8154–8155：默认 waitTime 7–15 秒传入搜索循环 Timer | 已有独立搜索门控，但 native 又把搜索/读取/买入统一加 3 秒间隔 |
| 单轮流程 | 8101–8122：auto actions → searchMarket → handleTransferResults → handleWonItems → 状态检查 → 周期性 Transfer/Watch List 整理 | search 和 buy 是分开的 scheduler turn；buy 重做两项库存读取 |
| 搜索结果 | 7698–7704、8305–8317：统计、页码及结果处理后交买入处理 | FCAT 返回明确实体/版本/挂单，任务再次进入 preflight |
| 买前判断 | 7586–7593：GK/化学风格/评分/已尝试挂单/过期/可选 Club/买卖价条件，随后 bid | FCAT 还有账号锁、跨模块 Journal、资金预留和精确身份保护，不能丢弃 |
| 固定价买入 | 7508–7511、2586–2589：计算可接受 bid/BIN，直接 services.Item.bid，没有统一买前 sleep 或强制两仓刷新 | 本次 87 为固定买价，重复读取与等待无报价需要 |
| 可选实时价 | 7676–7685、7852–7860：启用 findBuyPrice/findBidPrice 才另查价；可选 Club 排除也可能异步读取 | 不把所有 Enhancer 模式声称为零请求/零延迟；FCAT 百分比报价应在搜索前准备 |
| 买后等待 | 8285–8300：delayAfterBidFor 在 bid middleware 返回后执行，默认每搜索最多 1 张、0–0 秒 | 不能将它误当搜到第一张后要等的时间；多张/重试另受间隔约束 |

FCAT 的共享 traffic 层已按 `search` 和写操作分别门控：search 只设置搜索窗口，写操作检查 `nextWriteAt` 并预留下一写操作 +3 秒。因此“搜索刚返回”本身不要求再延后买入 3 秒。外层 native pace 则不区分它们。已有写操作冷却与全局暂停仍需保留，不应一律绕过。

### 已批准实施清单（2026-11-15）

用户已批准“更新文档后继续分步实施”。按以下步骤执行，不逐步请求用户验证：

- H1：统一Trading买入响应分类。先补403+461/缺码/矛盾证据回归，再接native、shared traffic、scheduler与明确提示；仅明确buy拒绝可竞争失败继续，其他模块保持原合同。
- H2：有界连续搜索→首笔买入。在同一账号/任务/native锁内最多串接一笔命中购买；只复用本轮搜索前完整库存快照，最终检查任何漂移均阻断。无命中及其余动作维持轮询公平性。
- H3：去掉该连续首笔买入的重复仓库读与通用3秒等待，保留共享写间隔及所有发送前Journal/停止/预算条件；失效命中丢弃后正常重搜。
- H4：贯通双任务、拒绝后新挂单、持久化期间停止、仓库变化、过期、冷却和未知回执；完整verify/离线Chrome及构建检查，专用安装精确源码后只读核验。用户仅最后验证真实成交。

范围：不调整报价/预算/搜索频率，不修改冻结EA trade adapter，不自动解除已有暂停或执行真实买卖。每阶段记录结果；未完成项保留，不用旧测试数量替代新场景。

用户追加要求参考返回值处理，已完成 [Enhancer错误链路对照](FC27_TRADING_87_REJECTION_20261115_ZH.md)。实施时必须同时覆盖native/共享traffic/scheduler三层，不能一边提速一边仍把HTTP403掩盖的竞购失败误归全局限流；明确拒绝、未知回执与下一次新挂单搜索分开验收。

1. **先做观测**：保留本轮 task-native 诊断，分开记录搜索响应、买入边界、EA 响应的时间与 HTTP/业务错误码；后续补 preflight/锁/Journal 阶段耗时。仅有边界批准不能冒充服务器已收到，未知回执不重发。诊断失败不影响业务。
2. **前置准备并连续处理命中**：在原账号/原生互斥下，搜索前完成 Unassigned/Transfer、容量、资金、买价和可选报价核验。搜索返回后，在同一连续执行段处理本次首个合格挂单，避免交给下一轮普通任务或插入整理动作。只为命中买入保留有界连续段，空结果/失败/等待立即释放，不能拿锁等下一次搜索。
3. **买前保留必要核验**：重新核账号/任务revision/停止、全局暂停、预算和持仓预留、精确实体/挂单/版本/实际价格/剩余时间；持久化唯一 intent 并回读后才发送。只复用本次搜索前的短期、上下文绑定库存快照，不提供跨轮无限缓存。若仓库 dirty/数量或余额变化、其他任务或原生写入、上下文/锁变化、超时、快照完整性未知，废弃命中快路径，重新核验再重新搜索，不能盲买旧挂单。
4. **拆开搜索节奏与买入节奏**：本次搜索后第一笔合格买入不再经过通用读请求 pace；仍使用共享写门控，真实前一笔写入冷却未结束则等待/重新搜索，401/限流/验证码/未知结果仍停。后续同一搜索多买、移卡和挂牌保留现有间隔，搜索额度与频率不提高。
5. **买后收尾**：原独立回读确认成交、移卡、按任务时间挂牌及 Journal 结算照常。后台维护、售出核对与 UI 更新安排在命中买入之后；不改变“买入后立即挂牌/定时卖出”的产品语义。零结果继续原搜索循环。

不采用“全局把 3 秒改为 0”，也不靠延长挂单有效期、提价、自动重发 403 或清账本解决延迟。此方案沿用 Enhancer 的搜索周期与命中处理分离，但保留 FCAT 已批准的多任务/预算/回执规则，并非宣称完整复制 Enhancer Trader。

## 验收与工作量

预计核心调度/前置快照与 native 接线约 1 个工作日；故障和跨任务贯通回归、离线 Chrome 与最新构建只读核验约 0.5–1 个工作日，真实金币操作最后由用户执行。不是仅改一个延迟常量。

- 固定买价、单任务命中：搜索响应到 bid 之间无额外 EA 读取、无新增 sleep；假时钟人为等待为 0。真实本地边界延迟目标 <500ms，需实测存储/锁耗时，不承诺 EA 响应或成交时间。
- 双任务：同一时刻只有一个精确买入；共享余额、每版本持仓、容量、定时窗口和累计预算不超额。多张买入/后续挂牌节奏不变。
- 搜索在途或 Journal 写入期间停止、编辑、切账号、跨页、另一模块写入、仓库失效：该买入必须被最终检查拦住或安全重新搜索。
- 原 search 空结果循环、数量限制、容量触顶本轮结束买入、真实冷却和流量上限行为不变。
- 403/461分别记录；明确拒绝、超时/失联未知、写账失败分别验证，已发送未知只核对，不再买。
- 原 Gallery/Puzzle/Streamlined 共用买卡和交易锁回归；冻结 EA trade adapter 不改。
