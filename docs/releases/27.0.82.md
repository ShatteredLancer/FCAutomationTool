# 27.0.82 — 少查无用卡、纯计算后台调度、缺货后置复查

## 现场与反馈环

用户 .81 的 Set75/Challenge115 已完成：方案估价 7,300，7 张实付 7,050。解题 79,075ms，其中五批报价耗时合计约 55.1 秒；最后一张在原 700 上限下连续查无挂牌，后来经用户重试批准后以 750 成交。报价上限本来不足不能自动解释成可买，不能偷把 700 提为 750。

三个先失败回归分别锁定：为完全无法出场的版本查价、浏览器纯计算仍用可被后台节流的零定时器、对同一卡连续用尽查询次数而没有先处理其他卡。

## 改动和边界

1. **只跳过可证明无用的位置候选。** 原生常规默契配置验证通过，且最低/精确默契高于 `3×(阵容人数−1)` 时，全队必须在可用位置。如 7 人至少 20 默契，一张完全不对位最多只剩 6×3=18。调用既有原生配置/普通卡上界验证后，才将与全部非砖位无交集的版本从查价和货币搜索中排除；库存估值覆盖也按同一可行集合计算，不把这些版本误报为未知市值。
2. 低默契（例如 7 人18默契）、非普通/不完整配置保留原池，不把位置偏好升级成通用硬限制。原品质、评分、国家/联赛/俱乐部、唯一版本、FSU 和主阵容保护仍完整验证。查询方向的原始资料不删除，.81 最多两页的低价覆盖仍在。
3. **纯计算浏览器调度改消息任务。** 相同生成器、节点上限和让出前后上下文复核；有浏览器文档/消息通道时优先 MessageChannel，任务后关闭端口，Node/缺通道环境保留原 timer 回退。没有缩短 EA 请求、买入、移动或等待间隔，也不保证浏览器/电脑真正冻结时继续运行。
4. **确认空挂牌后置一次复查。** 仅原生 Puzzle 购买启用。一次正常搜索确认上限内缺货后，先处理其余卡，末尾再在原上限和剩余额度内复查一次；仍受原持久化尝试次数上限约束。第二次仍无货就明确进入需用户重试的状态，不使用第三次相邻重复查询。
5. 只后置尚未发出买入的 waiting 卡。未知回执、未决买入/移动/保存、HTTP错误和明确拒绝的挂牌保留原处理，不进入后置队列；已购卡不重复买。显式停止/重开仍依赖持久化尝试记录和原核对。共享 Gallery/Streamlined 默认不开启该策略。
6. 增加持续的“暂缓缺货卡、最后按原限价复查”提示，区分缺货与程序错误。追加 seed/catalog/pricing/search/hint 阶段墙钟耗时及被证明无用的位置版本数，便于继续拆解网络与计算等待；search/hint 包含协作调度，不冒充纯 CPU 耗时。

- 同一私有冻结响应/价格与两张已持久化自有卡子集，发布版 .81 与本次源代码对比：估值均 5,200、默契均20；请求报价版本 100→83，基础+覆盖搜索节点 70,000→22,564，方向分析节点20,034→20,015。本地单组回放约647→285ms，仅为控制测量，不是现场79秒降为285ms，也不是当前价格或全库存验证。
