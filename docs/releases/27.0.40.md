# 27.0.40 Streamlined progress-read resilience

## Evidence and scope

The supplied 27.0.35 diagnostic confirms the first 30-card batch and 11,680 / 50,000 points through its response, receipt and independent readback. The second batch stops during pre-dispatch progress validation with `FC27_STREAMLINED_PROGRESS_READ_FAILED`. The old diagnostic does not contain the failed read's HTTP/native status, so it does not establish a specific network, rate-limit or server cause. This is not the earlier completion-reset failure.

## Changes

- Retry only the reviewed Streamlined progress GET after explicit transient transport/server statuses: 0, 408, 500, 502, 503, 504 and 520–524. At most three total attempts, with 1.5/3-second backoff and one shared 15-second deadline. A conflicting non-transient native error prevents retry.
- Authentication/rate-limit failures, unknown/business errors, 304, malformed payloads, changed context and changed methods remain blocking. Every successful read still requires fresh exact challenge/rule/score validation. No contribution, purchase, move or claim is retried by this change.
- Preserve the last confirmed journal in the UI when a later pre-dispatch progress read fails. Show confirmed points and keep completed batches disabled; recovery does not resend them.
- Export bounded HTTP/native error codes and attempt counts, without raw replies, physical identities or account data. Reconciliation request totals include retries.

All 27.0.36–39 ordinary Puzzle fixes are retained. Inventory priority, material protection, frozen settings/budget, transaction permissions, unresolved-receipt handling, Gallery and FSU remain unchanged. No journal migration, reset, new cycle or reward claim is introduced.

- Full `npm run verify`: 419 files, 4,889 tests passed, 39 skipped; syntax, lint, configuration, architecture, FSU, production build and distribution checks passed. Test concurrency was bounded to two workers without changing assertions or timeouts.

The narrow-screen screenshot was visually inspected. These use synthetic transactions, not real EA buys, moves, contributions or claims. Real-account acceptance remains pending after installation.
