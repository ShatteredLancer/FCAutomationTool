# 27.0.34 — 已完成贡献与本地收尾分开显示

## 现场证据

用户在 27.0.33 的贡献响应、持久回执和独立读回均成功，但随后本地
`contribution-finalization` 返回 `FC27_STREAMLINED_SET_CHANGED`。
用户进一步确认 SBC 实际已完成。旧 Journal 的分数尚未结清，不能把其
`currentScore:0` 当作 EA 没有收到材料。

## 修改

- EA 公开 `UTSBCFactory.createSet` 把服务端剩余秒数与每次本地时钟四舍五入
  后相加。重新读取 hub 可以产生一秒不同的正数到期时间，原逐秒相等
  检查会误报。仅在贡献确认后的计数同步中允许这种重投影；不把新到期
  时间写入页面，不延长冻结计划，也不改变贡献前的到期/目标检查。
- 原生 hub 的重复规则仍须一致，计数须是有效非负整数，到期类型须一致。
  坏字段改用固定的细分错误码，避免一个 `SET_CHANGED` 掩盖不同故障。
- 只有严格的独立读回通过后，收尾失败才返回只供显示的已确认分数。
  界面显示“SBC 已完成”或“本批贡献已确认”，明确仅本地同步待完成；
  分数和进度条不再退回旧 Journal 的 0。此信息也穿过采购桥接与恢复流程。
- Journal 仍保留待恢复状态，不根据提示文字结清已购卡、重新买卡或发出
  第二次贡献。恢复只重做读回和幂等本地收尾。回执未知、读回失败或材料
  仍在库存时，仍显示未确认，绝不套用成功提示。
- 日志的已验证读回/收尾阶段使用实际确认分数，私有物品/成交身份不导出。

保留库存优先、所有材料保护、预算和购买上限、FSU、普通 Puzzle/Gallery。
无新交易接口、自动领奖、重试贡献或自动清空旧记录。

## 验证与边界

先用公开原生 Set factory 重放出同码失败，并复现收尾失败没有成功提示；
修复后定向 7 文件 / 193 项通过，完整 `npm run verify` 通过：417 文件、
4,809 项通过、39 项跳过（进程内 `VITEST_MAX_WORKERS=2`，未改测试阈值）。
整套离线 Chrome 检查通过，新增完成提示、确认分数、禁用再次
贡献的回归，并目视检查窄屏截图。生产混合 Storage/Club 贯通覆盖正数到期
重投影、坏 hub 字段反复恢复后结清，全程仅一次合成贡献。

语法/未定义变量、配置/架构、FSU 重放和发布资产核对通过；root/dist
一致，1,859,704 bytes，SHA256：
`546e022860313e12246a32d2dc5a71409e07c74001ced739ffdda5722e0812b0`。

旧现场诊断未记录具体哪个 Set 字段不一致，因此不把到期
漂移重放说成已逐字段确认现场唯一根因；其他收尾故障也会准确区分状态。

没有操作真实账号买卡、移卡、贡献或领奖，也没有安装到用户浏览器。
用户确认的是 .33 的实际完成，不等于 .34 已通过账号验收。

## 更新与继续

覆盖更新原 FCAT 脚本，刷新 EA 页面。已经完成的 SBC 不要重新买卡或再投入；
有旧待恢复记录时点击“核对并恢复”，只检查既有结果并完成本地收尾。
若该 SBC 页面已下架，保留记录与诊断，不清空未决数据。
FSU Local 仍是 26.09.10。
